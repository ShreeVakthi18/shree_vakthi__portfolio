EAACD — Evolution-Aware Adaptive Cyber Defense

Detecting suspicious user activity · Mar–Apr 2026

What it does
A small web API that watches everything one user does in a session and gets stricter as that behavior drifts from normal: slow them down, limit them, then block them.
Why I built it
Most defenses judge each request on its own. A careful attacker can send requests that each look fine while the session as a whole is not. I wanted to see whether tracking the whole session would catch that.
How it works
The API keeps a behavior profile for each user and updates a risk picture with every request. The response escalates in steps: throttle, restrict, isolate. Isolate means an automatic HTTP 403, a reply that means "access forbidden".
Testing summary
52 normal requests passed with zero false positives (a false positive is a normal user wrongly flagged). Malicious sessions I generated were escalated within 4 requests. My own lab tests.
Limitations
These are not production benchmarks. I used traffic I generated myself, with no real users and no attacks I didn't think of.

REST APIBehavioral state machineRisk-driven detection engineCritical-asset mapping

Technical details

A REST API is a way for programs to talk to each other using HTTP requests. A behavioral state machine profiles each user across requests. The risk-driven detection engine maps critical assets, so activity near them raises risk faster. Enforcement escalates in three steps: throttle, restrict, isolate.

Architecture: how a request moves through EAACD
  1. Client request
  2. sends
  3. REST API
  4. updates
  5. Behavior profile
  6. risk picture
  7. Risk engine
  8. stage chosen
  9. Enforcement

The reply returns to the client: allowed, slowed, limited, or HTTP 403. The profile and risk picture carry over to the next request.

SHFSL 2.0 — Self-Healing File System Layer

Detecting and recovering changed files · Sep–Oct 2025

What it does
A file-protection layer that spots suspicious file changes and restores the original from a saved copy.
Why I built it
Catching tampering is only half the job, because an alert doesn't undo the change. I wanted the file to come back too.
How it works
A monitor running in the background watches file activity and scores how risky it looks. A snapshot (a clean saved copy of the file) is kept. When the risk score climbs, for example when someone touches a decoy file, the snapshot is copied back.
Testing summary
It detected all 6 attack scenarios I simulated, with risk scores up to 100/100. My own lab tests.
Limitations
I wrote those six scenarios myself, so they don't cover attacks I didn't think of.

PythonStreamlit dashboardMultithreaded daemonRule-based detectionAdaptive risk scoringEmail alerts

Technical details

A daemon (a program that runs in the background) intercepts file I/O in real time and applies rule-based detection with an adaptive risk score. A decoy file is a bait file nobody should open, so touching it counts as a strong sign of a breach. Guards stop a rollback from repeating and handle locked files. The Streamlit dashboard shows live risk scores, and email alerts are sent without blocking the monitor.

Architecture: how a file change moves through SHFSL 2.0
  1. File activity
  2. watched
  3. Monitor daemon
  4. scored
  5. Risk score
  6. score climbs
  7. Restore

A clean snapshot is saved beforehand. The Streamlit dashboard shows live risk scores, and email alerts are sent without blocking the monitor.

Wazuh SOC Home Lab

Investigating security alerts

What it does
A home SOC lab where I simulated failed logins on a Windows machine, had Wazuh detect them, and investigated the alerts.
Why I built it
I wanted to practice reading alerts the way a SOC analyst does, in a setup where I knew exactly what had happened.
How it works
Windows writes failed logins to its security log. Wazuh is a SIEM, a tool that collects security logs and helps analysts investigate alerts. It collects those logs, and a rule turns repeated failures into one alert.
Testing summary
I simulated a brute-force login (many password guesses in a row) against a Windows 10/11 machine. Wazuh alerted on the multiple failed logins, and I investigated later alerts, including a new local account and a privilege escalation. My own lab.
Limitations
One lab, one machine, attacks I ran myself. It shows I can follow alerts, not that I've handled a real incident.

WazuhVirtualBoxWazuh OVA imageWindows 10/11Windows security audit logging

Technical details

I deployed Wazuh from the official OVA (a ready-made virtual machine image) on VirtualBox. The Windows endpoint's audit logging fed Wazuh, a rule fired on multiple failed logins, and later alerts covered a new local account and privilege escalation. The repo has screenshots.

Network Vulnerability Audit

Finding network weaknesses

What it does
An audit of a Linux machine in my lab: which services were exposed, how risky each one was, and a script to close the worst ones.
Why I built it
Every open service is a possible way in. I wanted practice finding them, rating them and fixing them.
How it works
Nmap, a tool that finds open ports and the software behind them, probed the machine. I rated each finding, kept terminal screenshots and the raw audit log as evidence, then wrote a Bash script to harden the machine.
Testing summary
Nmap port, service-version (-sV) and OS (-O) scans of the lab target. The findings are in the table below. My own lab.
Limitations
One lab machine, with ratings that are my own judgment. It isn't a penetration test for a client.
Findings and the action taken
FindingMy ratingHardening action

Apache 2.4.7 (outdated version)HighDocumented; the script also automates updates
SMB, port 445 (file sharing, shown as filtered)MediumBlocked with UFW
SSH root loginHardening stepDisabled by the script

Technical details

UFW is Ubuntu's simple firewall tool. "Filtered" means something blocked or hid Nmap's probes, so it couldn't tell whether the port was open. The audit repo holds the risk table and evidence. The hardening script lives in its own repo.

Face-Recognition Attendance App Security Hardening

What it does
This is security work on a face-recognition attendance app that the company uses across the organization. I fixed 10 security issues in it and added 7+ security controls.
Why I built it
Many people rely on the app, so weak logins or loose handling of input would affect all of them.
How it works
The 10 issues covered authentication (logins), session management, input validation, the database and the API. The controls check each request before the app acts on it. The list is below.
Testing summary
I don't have numeric test results for this one. The changes are in the GitHub repo.
Limitations
Fixing 10 issues doesn't make the app completely secure. This was my work on one app during one internship, and I describe only my own changes here.
  • Rate limiting 5 attempts per 15 minutes. It restricts how many requests can be made in a set time, so password guessing becomes slow.
  • Request-size limit 2 MB per request, so huge inputs are refused.
  • Security headers 15 of them. These are instructions sent with each response that tell the browser to behave safely.
  • Logging Structured logs, so problems can be traced afterwards.
  • Error handling One shared place handles errors, so they are dealt with the same way everywhere.
